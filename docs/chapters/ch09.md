# Chapter 9: Alerts with Kafka and Mattermost

Goal: when a scan finds something serious, a message reaches team chat within seconds, and a chat outage never loses an alert.

Path: pipeline step -> receiver (checks token and repository) -> Kafka topics -> worker -> Mattermost channels.

## Steps

1. Resize the server: portal, Stop (deallocate), Size, F4as v6 (4 vCPU, 16 GiB), Start. Over SSH check:

        free -h
        nproc

2. Configure the alerts stack (the .env file is git-ignored and lives on the server only):

        cd ~/YOUR-REPOSITORY/platform/alerts
        cp .env.example .env
        sed -i "s/^MM_DB_PASSWORD=.*/MM_DB_PASSWORD=$(openssl rand -hex 24)/" .env
        sed -i "s/^RECEIVER_TOKEN=.*/RECEIVER_TOKEN=$(openssl rand -hex 24)/" .env
        sed -i "s#^ALLOWED_REPOSITORY=.*#ALLOWED_REPOSITORY=OWNER/REPOSITORY#" .env
        chmod 600 .env

3. Start Mattermost with its database, open the tunnel from the PC (leave it running) and set it up in a private browser window:

        docker compose up -d mattermost
        ssh -N -L 8065:127.0.0.1:8065 -L 8081:127.0.0.1:8081 -L 8080:127.0.0.1:8080 -i "$env:USERPROFILE\.ssh\devsecops-lab" azureuser@VM_PUBLIC_IP

   In Mattermost: admin account, team "SreeKode Labs", public channels security-high, security-review, pipeline-status, and one
   incoming webhook per channel. Put the three webhook URLs into .env as MM_WEBHOOK_HIGH, MM_WEBHOOK_REVIEW, MM_WEBHOOK_STATUS
   with the host changed to mattermost:8065 (the worker reaches Mattermost inside the compose network). Check nothing is left:

        grep -c "replace-me" .env      # must print 0

4. Start the rest, create the topics and send a test event:

        docker compose up -d
        bash create-topics.sh
        bash send-test-event.sh high

   Topics: security.high, security.review, pipeline.status, security.dead-letter. The warning about dots and underscores in
   topic names is normal. Kafka UI (http://localhost:8081 through the tunnel) shows the consumer group mattermost-notifier.

5. In GitHub add the variables ALERTS_ENABLED = true and ALERTS_URL = http://127.0.0.1:8000, and the secret ALERTS_TOKEN
   (the same value as RECEIVER_TOKEN, never shown on screen).
6. Copy the stage file over the pipeline, commit and push:

        Copy-Item stages\pipeline-ch09.yml .github\workflows\pipeline.yml
        git add .github\workflows\pipeline.yml stages\pipeline-ch09.yml
        git commit -m "ch09: send scan alerts to Kafka and Mattermost"
        git push

7. Reliability demo: stop the worker, send an event, watch the lag in Kafka UI, start the worker, watch the delivery:

        docker compose stop worker
        bash send-test-event.sh high reliability-1
        docker compose start worker
        docker compose logs worker | grep delivered

8. Tag and push: git tag ch09, git push --tags. Stop the VM (deallocate).

## What the pipeline does

- New step "Send events to the alerts receiver" (only when ALERTS_ENABLED is true) runs scripts/publish_events.py. It sits after the
  DefectDojo upload and before the gate (enforce), so a blocked run still sends its alerts.
- It sends four events from reports/summary.json: secrets, code (sast), image and the run status.
- The receiver accepts only the right Bearer token and the right repository, then puts each event on a topic.
- The worker posts to Mattermost, retries three times, then parks the message in security.dead-letter. A table of delivered
  event IDs suppresses duplicates.

## Notes

- Result: the main run is red (gate BLOCKED); the upload and alerts steps are green ("Queued 4 events in Kafka."). Chat shows the
  code and image findings for main and the BLOCKED status.
- After a server restart DefectDojo does not start by itself: run docker compose up -d in ~/django-DefectDojo first, or the upload
  step fails with "Connection refused". The alerts stack has restart: unless-stopped.
- send-test-event.sh may lack the executable bit: run it as bash send-test-event.sh.
- Kafka has no volume on purpose: messages survive stop and start, but docker compose down deletes them.
- The test event is a canned "demo findings" message, so the reliability event appears in chat with that text.
- Never put the token or the webhook URLs on screen or in Git. If one is ever exposed, rotate it.
- Size F4as v6 is about twice the hourly price of F2as v6 (portal: $213.16 against $106.56 a month). Resize back after Chapter 10.

## Done when

The pipeline run shows the alerts step green, the channels show the alerts for main, and the reliability demo ends with "delivered".
