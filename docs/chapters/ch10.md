# Chapter 10: Gated deployment to staging and wrap-up

Goal: the pipeline deploys the scanned app to a staging server, but only when the security gate allows it. Then we look back at the whole path and stop paying for the server.

Path: commit -> scans -> gate -> DefectDojo -> chat alerts -> deploy (only if the gate passed).

## Steps

1. Start the server (portal, Start). Size F4as v6 is only needed if you run the whole stack at once. Over SSH start DefectDojo and check the alerts stack:

        cd ~/django-DefectDojo && docker compose up -d
        cd ~/YOUR-REPOSITORY/platform/alerts && docker compose ps

2. In GitHub (Settings, Secrets and variables, Actions, Variables) add the variable DEPLOY_ENABLED = true. Without it the deploy job is skipped.
3. Read the new block in stages/pipeline-ch10.yml (see below), copy it over the pipeline, commit and push to main:

        Copy-Item stages\pipeline-ch10.yml .github\workflows\pipeline.yml
        git add .github\workflows\pipeline.yml stages\pipeline-ch10.yml
        git commit -m "ch10: deploy to staging only when the gate passes"
        git push origin main

4. Open the pipeline run for main (Actions, workflow "pipeline", not "hello"). Expected: Security result BLOCKED (13 high code findings, 11 critical image findings), the run is red, and the job "Deploy to staging" is skipped.
5. Bring the same commit to the testing branch and push:

        git push origin main:testing

   Expected: Security result ADVISORY, the run is green, and "Deploy to staging" runs.
6. Check staging on the server:

        docker ps --filter name=staging-juice-shop --format "table {{.Names}}\t{{.Status}}\t{{.Ports}}"
        curl -s http://127.0.0.1:3000/rest/admin/application-version

7. Tag and push: git tag ch10, git push --tags.
8. Resize back to F2as v6 and Stop (deallocate) the server so it stops costing money.

## What the pipeline does

- The scan job now publishes its image reference as a job output, so the deploy job runs exactly the image that was scanned (by digest), not whatever is newest.
- The deploy job has needs: scan and runs only when the scan job succeeded, the event is a push, and the variable DEPLOY_ENABLED is true.
- It starts the container staging-juice-shop on 127.0.0.1:3000 only (not reachable from the internet), with restart: unless-stopped, and waits up to 60 seconds for the application-version endpoint to answer. Early "Connection reset by peer" lines in the log are the wait loop retrying while the app starts.
- Gate policy: main is blocking, testing is advisory. In advisory mode findings are recorded in the report, DefectDojo and chat, not ignored. The gate passes, so the deploy runs.

## Notes

- Two workflows start on every push: "pipeline" is the real one, "hello" is the Chapter 3 test and can be ignored.
- A push can be rejected with "remote: fatal error in commit_refs". This is a temporary GitHub error: wait a minute and push again.
- If the main run shows the deploy job as skipped, that is the correct result, not a failure of the deploy.
- To show the staging page from your PC, open an SSH tunnel to port 3000 (as in Chapter 9). Never expose Juice Shop to the internet: it is vulnerable on purpose.
- Costs: F4as v6 is about twice the monthly price of F2as v6 ($213.16 against $106.56 in the portal). Deallocated VMs do not pay for compute, so stop the server when you are not working.

## Clean up when you finish the series

Do this only when you are sure you will not need the server again. Deleting is permanent: DefectDojo, Mattermost, Kafka data and the staging container all live on the server's disk.

1. In GitHub, in your own private repository: Settings, Actions, Runners, open the menu of the runner and choose Remove runner. After the server is gone it would only show as offline.
2. In the Azure portal: Resource groups, open the group that holds your lab (in these notes devsecops-lab_group), choose Delete resource group, type its name to confirm and delete. This removes the VM, its disk, the public IP address, the network rule and the virtual network in one step.
3. Do not delete only the VM. The disk and the public IP stay behind and keep costing a little every month.
4. The next day open Cost Management, Cost analysis and check that the charges for the group have stopped.
5. Optional: remove the lab variables and secrets from your private repository (DEPLOY_ENABLED, ALERTS_ENABLED, ALERTS_URL, ALERTS_TOKEN, the DefectDojo ones), revoke any token you created for the lab, and delete the lab SSH key pair on your PC.

A stopped (deallocated) server costs no compute, but the disk and the public IP are still billed. Deleting the resource group is the only way to reach zero.

## Done when

The main run is red with the deploy skipped, the testing run is green with the deploy done, staging-juice-shop answers on port 3000, and the server is stopped (deallocated).
