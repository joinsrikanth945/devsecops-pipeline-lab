# Chapter 7: Security gates by branch

Goal: the pipeline decides pass or block from the scan results, with a different policy per branch.

## Steps

1. Run the unit tests for the gate (10 tests must show OK):

        python -m unittest discover -s tests -p "test_gate.py" -v

2. Copy the stage file over the pipeline, commit and push to the `testing` branch:

        Copy-Item stages\pipeline-ch07.yml .github\workflows\pipeline.yml
        git add .github\workflows\pipeline.yml stages\pipeline-ch07.yml scripts tests
        git commit -m "ch07: add the security gate"
        git push origin testing

3. Testing branch: the run is green and the gate summary says ADVISORY (findings reported, nothing blocked).
4. Merge to main and push: the same findings now give BLOCKED and the run fails.
5. Change the rules: set repo variables BLOCK_ON_SAST and BLOCK_ON_IMAGE to `none`, run the workflow manually on main: PASS.
6. Tag and push: git tag ch07, git push --tags. Stop the VM (deallocate).

## What the pipeline does

- `scripts/gate.py summarize` reads the Gitleaks, Semgrep and Trivy reports and prints a decision table on the run summary.
- `scripts/gate.py enforce` is the last step (reports are always saved first) and fails the job on BLOCKED or ERROR.
- Results: PASS, ADVISORY, BLOCKED, ERROR.
- Defaults: ADVISORY_BRANCHES=testing, BLOCK_ON_SECRETS=1, BLOCK_ON_SAST=high, BLOCK_ON_IMAGE=critical. Repo variables override them.
- Only a direct push to an advisory branch is advisory; pull requests block.
- A missing or invalid report is ERROR on every branch.
- Severity mapping: Semgrep ERROR = high, WARNING = medium, other = low; Trivy severities are used as they are.
